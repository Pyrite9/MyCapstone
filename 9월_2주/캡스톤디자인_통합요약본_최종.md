## 1. 주제 선정 기준 (최종본)

### 1-1. 교수님이 제시한 기준 (원 기준, 최소 1개 충족)
(a) 세계 최초의 혁신적인 주제 / (b) 기존의 불편한 점을 개선하는 주제 / (c) 개인이 느끼는 불편함을 해결하는 주제

### 1-2. 우리 팀이 추가로 세운 필터
1. **데이터 자체 생성 가능** — 제3자 플랫폼 API(공공데이터포털 등)에 과도하게 의존하지 않음. (사례: 네이버 쇼핑검색 API 2026.7.31 종료로 무산된 아이디어 있었음)
2. **한 사람이 전체를 안 붙잡아도 굴러감** — 역할이 명확히 4인으로 쪼개질 수 있어야 함
3. **프론트-백엔드로 실질적인 역할 분리** — 백엔드만 있는 구조 지양
4. **위치·이동 경로 지속 추적 금지** (위치정보법 민감정보)
5. **건강·생체정보 등 민감정보 미취급** (개인정보보호법 민감정보)
6. **하드웨어 설치·현장 접근 필요한 도메인 제외**
7. **고객군이 업종을 안 가리고 넓어야 함** (4안 드랍 이후 신규 추가) — "그게 누구야?"라는 반문이 나오면 안 됨. (예: "팀플하는 대학" O / "24시간 서비스 운영하는 소규모 개발팀" X)
8. **개인 대상 서비스는 시장 포화 위험 매우 높음** — 개인용 생산성/습관/웰니스 앱 카테고리는 사실상 소진된 것으로 간주 (근거: 아래 4장 폐기 목록 참고)

### 1-3. LLM 사용 필터 (여러 차례 정정된 최종본, 중요)
- **처음에** Claude가 "LLM이 핵심이면 무조건 드랍"으로 과도하게 엄격 적용했으나, **관리자가 "애초에 LLM을 절대 쓰면 안 된다고 제약한 적 없다"고 정정.**
- **실제 기준**: ① 한 학기 안에 4인이 만들 수 있는 규모인가, ② 서비스 전체가 "AI에게 다 맡기는 껍데기"인가 아니면 그 위에 실질적 엔지니어링(도메인 로직/데이터 구조/역할 분리)이 있는가.
- **근거**: 실제 3ABA/3ABB 캡스톤 최종 발표 참고자료(2026.6.24, 같은 학과 졸업반) 확인 결과, 발표된 7개 팀 중 6개가 Ollama/RAG 등 로컬 LLM을 핵심 기능으로 정식 사용(AI문서초안생성, AI업무분해, AI그룹워크 복원 등). 즉 LLM 사용 자체는 전혀 문제 없음이 확인됨. 반대로 "AI 없이 순수 엔지니어링/프로세스 설계로 승부한 팀은 0개" — 이게 오히려 2안·발자국의 차별점("의도적으로 판단을 사람에게 남긴다")이 될 수 있음.
- **교수님께 직접 문자로 질의함(발송 완료, 2026.9.4 저녁 발송, 답변 대기 중)**: 지난 발표에서 LLM(다중 페르소나 LLM, LLM기반 문서기안도우미 등)을 핵심기능으로 쓴 팀이 대다수였는데 어떻게 생각하시는지, LLM을 활용한다면 어느 정도까지가 적정선인지 질의함.

## 2. 확정 주제 (2개)

### 2-1. 2안 — 원본 서류의 보존연한 관리 및 파기 이행 추적 시스템
- **배경**: 군 복무 중 보안문서 관리 경험. 법정 보존연한(의료법·상법·공공기록물법 등)이 담당자 재직기간보다 길어 인수인계 시 기한 정보 유실.
- **핵심 원칙**: 문서 **내용은 저장 안 함**, 관리번호·생성일·보존연한만 등록 → 기한 자동 산출 + 인계 시 책임 승계.
- **차별점**: 기존 솔루션(캐치시큐 등)은 전자파일 탐지·삭제 방식이라 물리 원본은 사각지대.
- **핵심 구현**: "기한 산출 엔진"(접근제어→기한산출엔진→알림스케줄러→기록저장소 구조).
- **상용화**: 대상고객 중소 의료기관·금융/법무/회계 사무소·공공기관·제조건설. 지불근거는 개인정보보호법 위반 과태료(3천만원 이하) 및 법적 분쟁 시 증빙 불가 리스크. 내부망 설치형 제공.
- **개발환경**: Spring Boot 3, Spring Data JPA, Spring Scheduler, Spring Security+JWT, PostgreSQL(구 사양은 ASP.NET Core Identity 옵션도 언급됨 — old.html 원본 참고).
- **산출물**: `2안_원본서류보존연한관리_보고서.docx`(공식 보고서, 9쪽), 업무기능도/업무흐름도 이미지 확보됨.
- **⚠️ 미해결**: old.html(원본 5안 슬라이드) 내용과 이후 재구성한 docx 보고서 내용 간 디테일 불일치(대상고객 범위, 과태료 수치, 기술스택 옵션) — 최신 기준 정리 필요.

### 2-2. 발자국(가칭) — 과제 산출물·완료확인 기반 동료평가 근거 제공 플랫폼
- **배경**: 조별과제는 보통 동료평가로 점수를 산정하지만 정작 과제 수행 "과정"에 대한 정보는 부재. 조사 결과 "조별과제 통합 관리" 카테고리 자체가 시장에 없음(노션·구글드라이브·카톡 조합으로만 때움).
- **핵심 원칙**: "판단은 사람이, 시스템은 근거만 제공한다." 점수 자동계산 절대 금지.
- **주요 서비스**: 과제 생성 및 역할 배정(조장이 역할 미리 지정 → 조원은 초대링크로 자동 배정, 자율선택 아님), 산출물 업로드(메타데이터만 저장), 진척 현황 시각화, 산출물 열람(조원·교수만, 조회 집계 안 함), 완료확인(산출물 없는 역할용), 동료평가(참고근거만 제시, 점수는 사람 입력).
- **4개 도메인**: 과제·역할 / 산출물 / 완료확인·평가 / 리포트·집계.
- **개발환경**: React, Spring Boot 3 + JPA, Spring Security+JWT, S3호환 스토리지, PostgreSQL.
- **상용화**: 대상 "팀 프로젝트를 시행하는 교육기관 전반". 지불근거는 교수(객관적 평가지표) + 학생(분담 편의성). 제공형태는 독립형 협업강의 플랫폼 우선, LMS 연동은 장기 확장(이번 개발범위 제외).
- **프로토타입 5종 완성**: 진척현황·완료확인·동료평가(기존 스크린샷) + 과제생성/역할배정/초대(신규 제작 HTML) + 산출물 보기(신규 제작 HTML, 3단 레이아웃). 전부 navy+amber+Noto Serif KR 브랜드 통일.
- **발표 슬라이드**: HTML 파일, v1→v15+ 수동편집 이어짐. 종이질감(paper texture)+잉크네이비+러스트오커 색상, Noto Sans KR 단일폰트, "히어로(큰타이포)+디테일" 2장 1세트 구조, 16:9 고정비율, 세로전환, 자동축소(autofit) 안전장치 내장. 21슬라이드(표지+배경/요지/상용화/프로토타입4종/시스템구조/개발환경). **최신본은 관리자가 수동 편집 중이므로 이어서 작업 시 최신 파일 기준으로 할 것.**
- **발표대본**: 1인칭 개인 발표용(주제 선정 평가받는 자리라는 맥락 반영), PDF 산출 완료(`발자국_발표대본_개인용.pdf`).
- **공식 보고서**: `발자국_동료평가플랫폼_보고서.docx`(10쪽, 스토리보드 5장 포함), 신규 제작 업무흐름도(Graphviz, 보라박스+주황핵심처리+다이아몬드 스타일) 포함.

## 3. 진행 중인 후보 (2개, 최종 확정 아직 아님)

### 3-1. "토막" (가칭) — 자습 일지 조각기록 서비스
- **한줄 요약**: 공부하다 남긴 토막글이 모여 자습 일지가 되는 서비스.
- **배경**: 야간자율학습(야자) 후 학교 지정 템플릿(오늘의목표/학습내용/문제풀이/자기평가/내일계획)으로 학습일지를 써서 LMS에 제출해야 하는데, 매번 백지에서 작성하는 게 번거로움.
- **핵심 흐름**: 야자 시작(타이머)→공부 중 태그(오늘목표/진행중/막힘/완료) 달아 조각 기록(시스템은 이해 안 함, 사람이 고른 태그대로만 배치)→야자 종료(시간 자동계산+조각이 템플릿 6칸에 원문 그대로 시간순 배치)→(선택)"다듬기" 버튼으로 조각을 문장으로 이어붙임(LLM, 보조 기능일 뿐).
- **LLM 안전성**: 다듬기 기능 빼도 서비스 성립(재료가 이미 정리된 상태로 충분히 유용) — "LLM 빼면 뭐가 남는가"에 "거의 다 남는다"고 답 가능한 설계.
- **4인 분업**: 세션·타이머 / 템플릿·매핑 / 문서조립 / 다듬기(LLM, 별도 서비스로 분리).
- **⚠️ 미해결**: 판매대상(개인 vs 학교 라이선스), 발자국과 같은 "교육기관" 도메인 중복 우려(큰 문제는 아님).

### 3-2. "잇다" (가칭) — 튜터-튜티 매칭 서비스
- **한줄 요약**: 과목별 튜터를 검색하고 신청하는 튜터-튜티 매칭 서비스.
- **배경(관리자 실제 경험)**: 학교가 매년 튜터링/멘토링을 상금 걸고 홍보하지만 문자·공지만 던질 뿐 매칭 지원이 전혀 없음. 선후배 커넥션이 동아리 외엔 생길 창구가 없어 매년 참여 저조. → 문제 본질은 "매칭 알고리즘 부족"이 아니라 "발견(디스커버리) 자체가 안 됨".
- **시장 검증**: 연세대·한국외대 등 대형 4년제는 자체 시스템(비교과통합시스템) 보유하나 그마저도 "전원 매칭 보장 안 함"을 공식 명시. 소규모/예산부족 대학은 시스템 자체가 없음(관리자 학교 포함 추정) — 이 사각지대가 타겟. 오이과외(K-12 외부 유료과외)·대학백과/메이저맵(입시생 대상)·에브리타임(구조화 디렉토리 없음)과는 구분됨.
- **구조 (배민 라이더-고객 비유)**: 튜터 화면(과목등록+성적인증→요청 수락/거절→활동기록) / 튜티 화면(과목검색→튜터목록탐색→신청→세션완료확인).
- **학교 연동 최소화 (중요 결정)**: 처음엔 운영자 대시보드도 고려했으나 범용성 위해 **관리자 화면 전체 제외**. 대신 로그인 없는 **엑셀/CSV 내보내기**만 제공 → 학교가 이걸로 상금지급 판단. "학교 공식 프로그램 창구"라는 지불근거는 유지하면서 개발범위는 축소.
- **4인 분업**: 튜터 도메인 / 튜티 도메인 / 매칭·알림 엔진 / 리포트 내보내기(Python/Pandas로 "과목별 매칭성사율", "튜터 부족 과목 TOP5" 등 통계 — 데이터분석 요소 자연스럽게 결합).
- **⚠️ 미해결**: 튜터 신뢰도 담보 방법(성적 인증 구체 방식), 튜터의 참여 유인(학교 상금 외 추가 동기 필요한지).

## 4. 폐기된 아이디어 전체 목록 (재검토 절대 방지용, 카테고리별)

### 4-1. 팀 초기(1차 발표 이전) 드랍
- 1안(채널배정/게임서버), 3안(무중단배포), 5안(프롬프트정제) — 교수 피드백 "혼자만 할 수 있는 개인 프로젝트" (5안은 이후 "LLM이라서"가 아니라 "학기 내 구현이 어려운 종류라서"로 정정됨)
- 4안(장애대응 당번관리, 온콜도구) — **최종 드랍**. 사유: "도입분야를 너무 한정했다, 수요층이 불분명하다" (24시간 서비스 운영 소규모 개발팀이라는 좁은 고객군이 원인)

### 4-2. 조직/업종 특화형 (넓은 고객군 조건 도입 이전 폐기)
