# 유가이력 서비스 명세

## 1. 개요
학교 주변 지역 주유소들의 가격을 매일 자동 수집해 DB에 누적하고, 각 주유소의 최근 평균가 대비 현재가가 얼마나 싼지/비싼지를 그래프로 보여주는 서비스.

## 2. 문제 정의
- 오피넷은 "지역/전국/정유사" 단위 평균 추이는 보여주지만, **개별 주유소 하나의 가격 히스토리 그래프**는 제공하지 않음 (공식 사이트 확인 완료)
- 운전자는 "지금 이 주유소가 평소보다 싼 편인지 비싼 편인지"를 판단할 근거가 없음

## 3. 핵심 기능

| 기능 | 설명 |
|---|---|
| 가격 자동 수집 | 매일 1회, 오피넷 오픈 API로 대상 지역 주유소 가격 수집 |
| 이동평균 계산 | 최근 N일(예: 7일/30일) 평균가 산출 |
| 가격 위치 표시 | "현재가가 이동평균 대비 몇 % 낮음/높음"을 라인 그래프로 시각화 |
| 주유소별 히스토리 | 특정 주유소 선택 시 그 주유소만의 가격 추이 그래프 제공 |
| 유종 전환 | 휘발유 / 경유 그래프 토글 전환 |

**주의**: "예측"이 아니라 "과거 대비 현재 위치 표시". 발표 시 "예측"이라는 단어는 쓰지 않는다 (오버클레임 방지).

## 4. 차별화 포인트
- 오피넷: 지역/전국 단위 "오늘 얼마나 싼가" → 우리 서비스: 주유소 단위 "이 주유소 자체가 평소보다 싼가"
- 그래프 컨셉: 주식 차트처럼 이동평균선 대비 현재가 위치를 시각적으로 표현

## 5. 시스템 구조

```
[Spring Scheduler] --하루 1회--> [오피넷 aroundAll.do API] --> [DB 저장]
                                                                    |
[React 프론트] <--REST API-- [Spring Boot: Controller-Service-Repository] <--조회--
```

- 백엔드: Controller - Service - Repository 표준 계층형 구조
- 수집: `@Scheduled`, 반경 기반 API(`aroundAll.do`)로 지역 내 주유소 일괄 수집
- 조회: `GET /api/stations/{id}/history?prod=B027&days=30` 형태
- 프론트: Recharts로 실제가격 라인 + 이동평균 라인 오버레이, 유종 토글 버튼

## 6. 외부 API 연동 상세

**사용 API**: 오피넷 반경 내 주유소 조회 (`aroundAll.do`)

- URL: `https://www.opinet.co.kr/api/aroundAll.do`
- 파라미터
  | 파라미터 | 설명 |
  |---|---|
  | certkey | 인증키 |
  | out | 응답 형식(xml/json) |
  | x, y | 기준 위치 좌표 (**KATEC 좌표계**, WGS84 아님 — 변환 필요) |
  | radius | 반경 (최대 5000m) |
  | prodcd | 유종 (B027: 휘발유, D047: 경유) |
  | sort | 1: 가격순, 2: 거리순 |
- 응답: 반경 내 주유소 목록을 배열로 일괄 반환 (UNI_ID, 상표, 상호, 가격, 거리, 좌표)

**API 이용 제한**: 일반 API 기준 **300call/일**

**콜 수 계산**
- 반경 하나(단일 구역) 기준
- 유종 2종(휘발유, 경유) × 수집 1회/일 = **하루 2콜**
- 하루 3회 수집으로 늘려도 하루 6콜 — 300call/일 대비 충분한 여유
- 향후 반경을 여러 구역으로 확장할 경우에도 콜 여유 충분 (1차는 단일 반경으로 검증 후 확장 여부 판단)

## 7. DB 설계 (초안)

**PriceHistory 테이블**
| 컬럼 | 설명 |
|---|---|
| id | PK |
| uni_id | 주유소 고유코드 (오피넷 UNI_ID) |
| prod_cd | 유종 (B027/D047) |
| price | 판매가격 |
| collected_at | 수집 일시 |

복합 기준: `(uni_id, prod_cd, collected_at)`으로 이력 누적

## 8. 기술 스택
- Backend: Spring Boot 3, JPA
- Frontend: React, Recharts
- DB: RDB (MySQL 등, 팀 표준에 맞춤)

## 9. 필터 점검 결과

| 필터 | 결과 |
|---|---|
| 이미 존재하는가 | 오피넷 등 국내 공공 서비스 확인 결과 없음 (검증 완료). 국내 민간 앱(오일나우 등) 추가 확인 권장 |
| LLM 의존도 | 없음 — 순수 데이터/통계 기반. LLM 필터 문제 없음 |
| 콜드스타트 | 없음 — 서버가 자동 수집, 사용자 수와 무관하게 며칠 내 가치 발생 |
| 팀 기술 수준 | 적합 — 스케줄러 + CRUD + 차트 라이브러리 수준, 초보 팀 완주 가능한 난이도 |

## 10. 범위 (1차 데모 기준)
- 지역: 학교 주변 반경 1개 구역 (최대 5000m)
- 유종: 휘발유, 경유 두 종류
- 수집 주기: 하루 1회 (구현 검증 후 확장 검토)
- 반경 확장은 구현 안정화 이후 판단 — 현재는 넓혀도 데모 상 의미 증가가 크지 않다고 보고 보류

## 11. 남은 검증/숙제
- [ ] 국내 민간 앱(오일나우, 카택스 등 오피넷 제휴 스타트업) 중 유사 기능 있는지 확인
- [ ] 학교 좌표(WGS84) → KATEC 좌표 변환 방법 확정 (라이브러리 또는 변환식)
- [ ] 데모용 대상 반경(대구/학교 주변) 확정 및 초기 시드 데이터 확보 방식 결정
- [ ] 수집 주기 하루 1회 시 그래프가 너무 계단식으로 밋밋하지 않을지 목업으로 사전 테스트



# 책바퀴 서비스 명세

## 1. 개요
학교 특화 전공서적 중고거래 서비스. 학과/과목 단위 태그 검색으로 필요한 교재를 빠르게 찾고, ISBN 입력만으로 책 정보를 자동 완성해 등록 부담을 줄인다.

## 2. 문제 정의
- 에브리타임 중고장터, 당근마켓 등 범용 중고거래 플랫폼은 사진+제목 위주 게시판이라 "내가 다음 학기 들을 과목의 교재"를 찾기 비효율적
- 기존 학술 선례(BookCue 등)도 존재하나, 우리 학교 특화 + 과목 매핑 구조로 차별화

## 3. 핵심 기능

| 기능 | 우선순위 | 설명 |
|---|---|---|
| ISBN 자동 등록 | 필수 | ISBN 입력 시 책 정보(제목/저자/출판사/표지) 자동 완성 |
| 전공 태그 검색 | 필수 | 학과/과목 기준으로 게시글 필터링·검색 |
| 재학생 인증 | 필수 | 학교 이메일 인증으로 재학생만 가입 가능 |
| 거래장소 고정 | 권장 | 캠퍼스 내 지정 장소(중앙도서관 앞 등) 중 선택 |
| 거래가격 주간평균 | 선택 | 동일 도서의 과거 거래가 평균 제공 (콜드스타트 영향 있음) |
| 관심교재 알림 | 선택 | 찜한 책 등록 시 알림 (초기엔 마이페이지 확인 → 여유되면 이메일 알림) |

## 4. 차별화 포인트
- 에브리타임: 범용 중고장터, 검색이 제목/사진 의존적
- 책바퀴: 학과-과목-교재 매핑 구조로 "내가 들을 과목" 기준 검색 가능 + ISBN 자동 등록으로 등록 장벽 최소화

## 5. 시스템 구조

```
[사용자] ISBN 입력
    → [Spring Boot] 네이버 책 검색 API 호출 (query=ISBN)
    → 결과 있음: 제목/저자/출판사/표지 자동 채움
    → 결과 없음: 수동 입력 폼으로 전환
    → [등록] 학과/과목 태그 선택 + 가격/상태 입력
    → [DB 저장]

[사용자] 검색/필터
    → [React] 학과/과목 태그 선택 → [REST API] → [DB 조회] → 목록 렌더링
```

- 백엔드: Controller - Service - Repository 표준 계층형 구조
- 프론트: 게시글 목록/상세, 학과·과목 필터 UI, 검색

## 6. 외부 API 연동 상세

**ISBN 조회: 네이버 책 검색 API (메인)**
- URL: `https://openapi.naver.com/v1/search/book.xml` (또는 `.json`)
- 인증: `X-Naver-Client-Id`, `X-Naver-Client-Secret` 헤더
- 파라미터: `query`(ISBN 문자열 입력), `display`, `sort`
- 반환: 제목, 저자, 출판사, 표지 이미지, 가격 등
- 호출 한도: 개인 개발자 기준 통상 넉넉함(등록 시점에만 호출되는 구조라 부담 적음)

**대안/폴백: 국립중앙도서관 서지정보 API**
- ISBN 단건조회 전용 API, 네이버 검색 결과 없을 때 2차 목표로 연동 고려
- 응답이 MARC 계열이라 파싱 부담 있어, 1차 구현 범위에서는 제외

**참고**: 기존에 검토했던 알라딘 Open API는 서비스 종료되어 사용 불가 (확인 완료)

## 7. 인증 설계

- 재학생 인증: 학교 이메일 도메인(`@학교도메인`) 기반 인증 메일 발송 방식
- **확인 필요**: 학교 이메일 도메인 실제 존재 여부. 없을 경우 학번+이름 매칭 등 대체 인증 수단 검토
- 구현 범위: 이메일 인증 로직(SMTP 연동)은 팀 리소스 상 부담이 있을 수 있어, 우선순위는 두되 일정 여유 보고 최종 확정

## 8. DB 설계 (초안)

**User**: 사용자 정보, 인증 상태
**Department/Course**: 학과-과목 마스터 데이터 (초기엔 수동 등록)
**BookPost**: 제목, ISBN, 저자, 출판사, 표지URL, 가격, 상태(판매중/예약중/판매완료), 작성자, 과목 태그
**WishBook**: 관심교재 등록 (사용자-도서 매핑)

## 9. 필터 점검 결과

| 필터 | 결과 |
|---|---|
| 이미 존재하는가 | 에브리타임·당근마켓 등 범용 플랫폼 존재. 학과-과목 매핑 구조로 차별화 필요 (발표 시 필수 방어 포인트) |
| LLM 의존도 | 없음 — 표준 CRUD + 외부 API 연동 구조 |
| 콜드스타트 | 있음 (양면시장) — 팔 사람·살 사람 둘 다 필요. 초기 데이터는 조원 보유 교재로 시드 예정 |
| 팀 기술 수준 | 적합 — CRUD, 외부 API 연동(네이버), 태그 필터링 수준. 초보 팀 완주 가능 |

## 10. 콜드스타트 대응 전략
- 데모 초기 데이터: 조원들이 실제 보유한 전공교재로 채워서 학과 특화 커뮤니티로 시작
- 거래가격 주간평균 기능은 최초 등록가를 기준값으로 표시하고, 거래 완료 건이 쌓이면 갱신되는 구조로 설계 (데이터 없을 때도 화면 공백 방지)
