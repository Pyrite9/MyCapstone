## 2. 주제 선정 기준
 
### 2-1. 심의 교수 기준 (참고)
(a) 세계 최초 혁신 / (b) 기존 불편 개선 / (c) 개인 불편 해결 — 최소 1개. 담임교수에겐 적용하지 않음.
 
### 2-2. 팀 필터
1. 데이터 자체 생성 가능 — 제3자 API 과도 의존 금지 (네이버 쇼핑검색 API 종료로 무산된 전례)
2. 한 사람이 전체를 안 붙잡아도 굴러감 — 역할 분할 가능. **사용자 도메인을 아는 사람이 팀에 한 명뿐이고 조원이 사용자가 아니면 제외** (2안 탈락 사유)
3. 프론트-백엔드 실질 분리
4. 위치·이동 경로 지속 추적 금지
5. 건강·생체 등 민감정보 미취급
6. 하드웨어 설치·현장 접근 필요 도메인 제외
7. 고객군이 넓어야 함 — "그게 누구야?" 반문이 나오면 탈락
8. 개인용 생산성/습관/웰니스 앱은 포화로 간주
9. 양면시장·크라우드소싱형 콜드스타트 경계
### 2-3. 5→3 압축 기준 (평가자 성향 모르는 담임교수 전제)
- 하드: ① 6명·6개월 병렬 작업량 ② 데이터 자체 생성 ③ 학기 안 데모 ④ 선배 졸업작품 중복 없음
- 소프트: ⑤ "기존 서비스가 구조적으로 못 하는 것" 한 문장 ⑥ 뽑혔을 때 조원이 움직이나 ⑦ 3개가 서로 다른 축 ⑧ 살을 붙일수록 강해지는가
- **기준으로 쓰지 않는 것**: 상용화 순위(발표 슬라이드 한 장 분량, 개발 난이도 예측 못 함), 이전 심의 교수의 반응, LLM 활용도, 1차 통과 여부
- 투표 해석: 복수선택에서 안 찍은 건 "덜 좋다"지 "싫다"가 아님. 거부 강도는 단일선택 제외 투표로 따로 잼.
### 2-4. 검증 원칙
- 시간축 콜드스타트(이력이 쌓여야 가치 생기는 서비스)는 한 학기 데모 불가 → 구조적 기각.
- 타겟 재조정 시 실측 검증. 직관이 통계와 반대로 나온 사례(1인 가구 건조기) 있음.
- "기술은 있는데 안 쓰이는 문제" ≠ "제품 공백". 운영 관행 문제는 캡스톤 대상 아님.
- "이미 있다/없다"는 공식 사이트·앱 직접 확인까지. 검색 한두 건으로 탈락시켰다가 뒤집힌 사례(유가이력) 있음.
### 2-5. LLM 사용 기준
- 심의 교수 답변(2026.9.8) `[확정]`: LLM 사용은 필수 아님, "필요하면 적극 활용". 원리(프롬프트·RAG·임베딩·벡터 DB) 기본 이해는 필요, 깊이는 불필요.
- 팀 자체 기준 "LLM 빼면 뭐가 남는가"는 교수 요구보다 엄격한 자체 기준.
- 3주제에 LLM 없음. "LLM 어디 쓰냐" 질문 대비 주제별 보조 기능 한 줄(책바퀴 과목명 자동완성 보조, 잇썸 모집글 작성 보조) 준비. 핵심 기능으로 승격시키지 않음.
- 같은 학과 2026.6 졸업발표 7팀 중 6팀이 로컬 LLM 핵심 사용, 순수 엔지니어링 팀 0 → "판단은 사람에게" 설계가 차별점.

## 3. 최종 3주제 (담임교수 컨펌 대상)
 
상세는 `캡스톤_주제명세.pdf`가 기준. 여기엔 결정 사항과 v2 대비 변경만.
 
### 3-1. 발자국 — 조별과제 과정기록 & 평가지원 서비스
- 원칙: **판단은 사람, 시스템은 근거만.** 점수 자동 계산·순위·가중치 없음. PC 웹.
- **파일 본문 저장함** `[확정]` (v2의 "메타데이터만"은 오기). 버전 순 저장, 최신 상단, 조원·교수 열람·다운로드, 조회·다운로드 집계 안 함. 오브젝트 스토리지 사용.
- **과제 하나에 조 여러 개.** 교수가 과제 생성·조마다 조장 지정, 조장이 역할 배정(초대 링크) `[Claude 초안, 관리자 확인]`. 권한 모델은 조 단위.
- 완료확인은 산출물 없는 **기여 항목**(회의 진행·자료 취합·일정 조율)에도 적용. 담당자 보고 → 다른 조원 확인, 여러 명 가능.
- 동료평가 2항목(역할 수행/팀 소통) 각 5점 척도, 개별 입력, 조원 간 비공개, 결과는 교수만 열람. 근거 패널(산출물·완료확인 종류별 분리)은 조원·교수.
- 고정 문구 "업로드 횟수는 기여도가 아닙니다 · 점수는 시스템이 계산하지 않습니다".
- 예상 작업량 메모 제외 `[확정]`. 본교 LMS에 동료평가 기능 없음(서면·구글 폼).
- 근거: 조원 4명 중 3명 "파일로 남지 않는 기여 미반영", 1명 "친분·발언권 편향".
- 기술 핵심 과제: 조 단위 권한(Spring Security 메서드 인가). 그 외: 파일 업로드·스토리지·버전.
- `[구현 단계]` 교수 계정 생성 방식, 데이터 보관 기간(Q6은 "교수와 협의").
### 3-2. 잇썸 — 캠퍼스 한정 식사약속 플랫폼
- 차별점: **재학생 인증 + 학과 고정 노출로 만든 학교 한정 신뢰망.** 유사 서비스 4개(밥친구·밥풀·같이먹자·헝글) 중 재학생 인증을 가입 조건으로 두는 곳 없음 `[확정, 09.12 검색]`. "최초", "지역 개방형은 구조상 불가" 표현은 문서에 쓰지 않음.
- 매칭 대상은 사람이 아니라 **자리**. 목록엔 자리만, 상세에서 사람 공개. 콜드스타트 방어 문장.
- 완료 확정: 약속 시각 → 방장 체크리스트 → 미체크 노쇼. 방장 10분 미확정 시 자동 종료, 노쇼 판정 없음, "미확정 종료" 보존 `[확정]`.
- 정원은 참여 신청 시점 차감·취소 시 복구 / 조건(성별·나이대) 있는 모집은 해당 정보 공개 회원만 참여 / 신고 → 팀 수동 확인·계정 정지 `[Claude 초안, 관리자 확인]`.
- 마이페이지 거리 설정 제외 `[확정]`. 메뉴 카테고리 목록은 구현 단계, 취향태그는 메뉴 카테고리 연동 `[확정]`. 온도지표 산식 구현 단계.
- 기술 핵심 과제: 정원 동시성(트랜잭션 격리·JPA 락). 그 외: WebSocket 채팅, 스케줄러.
- 1차 제외: 친구 추가, 빈자리 알림, 맛집 추천, 허위 노쇼 이의 제기.
### 3-3. 책바퀴 — 캠퍼스 전공서적 중고거래 플랫폼
- 차별점: **학과-과목-교수 매핑 검색 + 판매완료 이력 기반 시세.** 에브리타임은 텍스트 검색은 되므로 "검색이 안 된다"고 말하지 않음. "판매자가 같은 학교 학생인지 보장 안 됨"은 에타가 학교 인증을 하므로 삭제.
- 매물 등록: ISBN → 네이버 책 검색 API 자동 채움(대체: 국립중앙도서관 ISBN 서지정보 API, 알라딘 API 종료). 사진은 오브젝트 스토리지 `[확정]`.
- 상태 전이 판매자만: 판매중 → 예약중 → 판매완료, 예약 취소 시 판매중 복귀. 완료 매물은 목록 숨김·이력 보존 → 시세(최근 거래가 구간+건수) `[Claude 초안, 관리자 확인]`.
- 신고 → 팀 수동(매물 숨김·계정 정지) `[Claude 초안]`. 제본 교재 문구는 문서에 넣지 않음 `[확정]`.
- 마스터 데이터(학과·과목·교수): 1차는 AI소프트웨어과 한 학기분, 학과 시간표 기준 수동 입력. 학기 갱신·타 학과는 기능 확장.
- 기술 핵심 과제: 유사도 검색(pg_trgm, GIN 인덱스, 네이티브 쿼리). 그 외: 채팅, 외부 API 대체 처리, 이미지 업로드.

## 4. 제외·이관·보류
 
- **유가이력** → 캡스톤 제외, **관리자 개인 프로젝트로 이관** `[확정]`. 사유: 화면 2개·채팅·알림·권한 없음으로 6인 분업 불가 + 오피넷 단일 의존. 개인 스택(.NET/PostgreSQL/Docker/Redis)으로 진행. 스펙(학교 반경 주유소 풀, 일 1회 수집, 이동평균 차트, GPS·지도 UI 없음, 창업기업 제휴 트랙)은 v2 4-2 절 참조 — 개인 프로젝트 문서로 분리 예정.
- **2안(원본 서류 보존연한 관리)** → 제외 `[확정]`. 사유: 도메인 경험자가 관리자 1명뿐, 조원이 사용자가 아니라 검증·판단 불가, 결정이 한 사람에게 몰림. 산출물(보고서 docx, 목업 2장, 보완 덱)은 참고용 보관. 법령 3건·과태료 `[미검증]` 그대로.
- **토막** — 백업. 잇썸 반려 시 명세 착수. 명세 미작성.
- **잇다** — 상태 미정리(기각 기록 없이 후보에서 빠짐).
- **빨래 스케줄링** — 타겟 실패로 사실상 보류.
- 경험 부재 보류: 공용물품 대출 기한 추적, 검수·납품 확인, 외주 리비전 추적, 동아리 신입 모집.

## 6. 명세서(PDF) 형식 `[확정]`
 
- 판형·서체·표·그림·목업·툴체인 규칙은 `capstone-presentation-style_v3.md` **§13**. 여기엔 구조와 원칙만.
- **설계 문서형**, 발표 자료 아님. 구조: 표지(학과·과목·학기 / 제목 / 팀 6명 / 문서 버전) → 차례 → 1 발자국 → 2 잇썸 → 3 책바퀴 → 4 부록. **공통 절 없음**(스택·인증·채팅·지도는 주제별 x.1). 문서 목적·선정 과정·비교표·용어 모음·시연 계획·ERD 제외.
- 주제 절 동일 구조: x.1 정의 / x.2 문제 / x.3 기존 서비스 / x.4 기능 / x.5 화면 / x.6 구조·엔티티 / x.7 범위(1차 핵심·1차 부가·구현 순서·기능 확장) / x.8 기술 과제(과제·왜 어려운가·배워야 할 것·그 외) / x.9 리스크 / x.10 예상 질문. 단순 넘버링(x.4.n).
- **문서에 쓴 건 전부 질문 대상 — 조원 누구든 답할 수 있는 것만.** "근거 아직 없음, 채택 시 조사" 같은 자백성 문장 넣지 않음.
- 강제 페이지 넘김: 1.9, 2.4, 2.5, 2.6, 2.9, 3.6 엔티티, 3.7, 3.9.
