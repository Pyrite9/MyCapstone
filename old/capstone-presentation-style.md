# 캡스톤디자인 — 프레젠테이션 스타일 명세

> 대상: 캡스톤디자인 팀 발표자료 전체 (2안, 발자국, 토막, 짠밥 등 후보 주제를 한 발표 안에서 다룸)
> 원칙: 팔레트·타이포·모티프·상호작용 규칙은 **모든 주제 섹션에 동일하게 적용**한다. 주제마다 바뀌는 건 텍스트·아이콘·데이터뿐, 구조 규칙은 안 바뀜 — 그래야 여러 후보를 한 덱에서 다뤄도 "한 팀이 만든 발표"로 읽힘
> 기존 자산: HTML 16:9 덱, Noto Sans KR

## 0. 컨텍스트

- 발표 주체: 공학계열 개발자 팀 (React/Spring Boot 스택, LLM 활용 프로젝트가 공통 요구사항)
- 청중: 담당 교수 + 동급생 — 기술 심사보다 서비스 타당성/완성도 심사에 가까움
- 톤: 신뢰감 + 실용성. "번지르르한 스타트업 피치" 아니고 "이 팀이 실제로 구현할 수 있다"는 인상이 우선
- 후보 주제마다 LLM이 서비스 핵심인 경우가 많음 — "LLM 빼면 아무것도 안 남는다"는 인상을 피해야 함 → 어떤 주제든 LLM은 도구로, 데이터/로직/UX가 주인공으로 보이게 구성

## 0-1. 테마 고정

- **다크모드 대응 금지.** 시스템 설정과 무관하게 항상 라이트 테마 (`color-scheme: light only`)
- 발표 환경(강의실 스크린, 프로젝터)에서 다크 배경은 가독성이 떨어지고, 화면 밝기 대비도 예측 불가 → 라이트 고정이 안전

## 1. 팔레트

특정 주제의 은유(예: "발자국=경로")에 종속시키지 않는다. 팀 정체성 — 정확하고 절제된 엔지니어링 태도 — 을 기준으로 잡은 무채색 우위 팔레트. 파랑/보라 계열 SaaS 디폴트, 초록=성장 같은 뻔한 주제 은유 배제.

| 역할 | 색 | 비중 |
|---|---|---|
| 베이스 | `#EDE9E3` (웜 그레이) | 배경 전체 |
| 주 색상 | `#332C4A` (딥 플럼) | 60-70%, 제목/주요 도형 |
| 보조 | `#9C8B72` (타우프) | 20%, 서브텍스트/보조 도형 |
| 강조 | `#B8863B` (머스타드 골드) | 5% 이하, 진짜 강조할 지표/CTA만 |
| 텍스트 | `#211D2B` (완전 블랙 아님, 플럼 톤 섞음) | 본문 |

- 이 팔레트는 **모든 후보 주제 섹션에 동일 적용**. 주제별로 색을 바꾸지 않는다 — 바꾸는 순간 한 팀의 발표가 아니라 짜깁기로 읽힘
- 강조색은 "이 발표에서 제일 중요한 숫자 1개" 같은 곳에만. 버튼마다 칠하면 그 순간 의미 없어짐

## 2. 타이포그래피

- 단일 패밀리: **Noto Sans KR**
- 위계는 두 번째 서체가 아니라 **weight + 크기 + 자간**으로만:
  - 타이틀: Black(900), 큰 사이즈, 자간 살짝 좁게
  - 본문: Regular(400)/Medium(500)
  - 라벨/캡션: Medium(500), 작게 — **절대 all-caps로 안 씀**
- 한 슬라이드에 폰트 굵기 3단계 이상 쓰지 않기

## 2-1. 크기 규칙 (프로젝터 · 뒷자리 가독성)

강의실 뒤쪽에서도 읽혀야 함 — vw 기반 clamp()를 쓰더라도 **최솟값(하한)을 아래보다 낮게 잡지 않는다.**

| 역할 | 최소 크기 | 권장 범위 | 비고 |
|---|---|---|---|
| 타이틀(H1) | 48px | 48–76px | 900 weight |
| 섹션 제목(H2) | 32px | 32–44px | 900 weight |
| 소제목(H3, 단계/항목명) | 22px | 22–28px | 700 weight |
| 본문(설명 텍스트) | **20px** | 20–24px | 뒷자리 가독성 마지노선, 절대 이 밑으로 안 내림 |
| 캡션/메타 (부가정보, 페이지 표기 등) | 14px | 14–16px | 핵심 정보 아닌 것만 여기로 |

- 본문 설명이 20px 밑으로 내려가야 할 만큼 텍스트가 많다면, 크기를 줄이지 말고 **문장을 줄이거나 슬라이드를 나눈다**
- 캡션 등급은 "안 읽혀도 발표에 지장 없는 정보"에만 씀

## 2-2. 줄바꿈 규칙

자동 줄바꿈 자체를 막을 수는 없음 — 대신 삐져나오지 않게 세 겹으로 보장:

1. **어절 단위 줄바꿈 고정**: 전역으로 `word-break: keep-all;` (한글이 글자 단위로 끊기는 것 방지). `overflow-wrap: break-word;`는 긴 영단어/URL 방어용으로만 같이 둠
2. **role별 max-width 강제**: 2-1 크기 표의 role마다 컨테이너 폭을 고정
3. **콘텐츠 확정형 텍스트는 줄바꿈 위치를 `<br>`로 명시**: 저작 시점에 눈으로 확인한 지점에서 끊음. 텍스트 수정 시 `<br>` 위치도 같이 재확인
   - 텍스트 길이가 계속 바뀌는 동적 콘텐츠라면 자동 축소(JS)가 필요하지만, 확정 콘텐츠 위주인 이 프로젝트에선 불필요

## 3. 위계 표현 수단 (밑줄·컬러바 금지 대안)

- 제목 강조: 밑줄/컬러바 대신 **베이스 색과 다른 톤의 배경 블록**으로 타이틀 영역을 구분
- 섹션 전환: 컬러 스트라이프 대신 **여백 확대 + 배경색을 베이스↔딥플럼 반전**
- 카드/박스 구분이 필요하면 border-radius 통일하지 말고, 딱 하나의 형태(예: 각진 사각형, radius 0)로 고정 — "카드 킷" 느낌 배제

## 3-1. 페이지 인디케이터 (콘텐츠 모티프 아닌 UI 관례)

- 원형 점 대신 **가로 pill 바**: 비활성은 짧고 낮은 투명도, 활성은 옆으로 넓어지며 `--primary`로 채움 (워크스페이스 인디케이터 느낌)
- 내비게이션 UI라 콘텐츠 장식 규칙과는 별개 — 다만 원형 금지 기조와 자연스럽게 맞음

## 4. 공통 모티프 — 시스템 다이어그램 트레이스

주제 은유가 아니라 **팀의 정체성(개발자 집단)**에서 모티프를 가져온다: 개발자는 프로세스를 아키텍처/회로 다이어그램처럼 그린다. 어떤 후보 주제든 "이건 시스템이다"라는 인상을 준다는 점에서 범용적으로 성립함.

- 모티프: 단계·구성요소 사이를 **직각으로 꺾이는 연결선**(회로 트레이스 / 아키텍처 다이어그램 커넥터)으로 잇는다. 곡선·점선 대신 직선 + 직각 코너
- 이 연결선 모티프 하나만 전 슬라이드·전 주제 섹션에 반복 — 주제마다 다른 장식 모티프를 새로 만들지 않기
- 프로세스가 실제 순차 구조일 때만 번호 마커 사용 (01/02/03…) — 순서 없는 나열에 억지로 번호 붙이지 않기
- **마커는 원형으로 감싸지 않는다.** "컬러 원 안에 숫자/아이콘" 조합은 목차·단계 표시의 디폴트 클리셰라 배제
  - 대체 방향: 연결선 위/옆에 숫자를 도형 없이 그대로 얹고, 숫자 옆에 짧고 굵은 tick(회로 단자 느낌)만 둔다. 감싸는 배경·테두리 없음
  - 강조가 필요한 단계는 tick 두께나 숫자 색만 바꿔서 표현

## 5. 절대 금지 (매 슬라이드 재확인)

- 제목 밑줄, 엣지 컬러 바/스트라이프, 카드 한쪽 면 보더
- 모든 카드에 동일 radius + 동일 회색 그림자
- **원형 아이콘/숫자 배지** — 컬러 원 안에 숫자나 아이콘을 넣는 목차·단계 표시. 모든 형태의 "colored circle + icon/number" 조합 전면 배제
- **타이틀 위 eyebrow 라벨** — 불릿 점 + 자간 넓힌 ALL-CAPS + 미들닷(·) 조합. 셋 중 하나만 써도 클리셰로 읽히니 개별 요소도 재사용 금지
  - 컨텍스트 표기가 꼭 필요하면: 라벨화하지 말고 슬라이드 하단 구석에 작은 크기·낮은 대비 텍스트로만
- **개발자 클리셰 장식도 금지**: 모노스페이스 폰트로 라벨 꾸미기, 터미널 프롬프트(`$`) 아이콘, `</>` 아이콘, git diff 스타일 +/- 색상 배지 — "개발자 팀"이라는 정체성을 문자 그대로 코드 장식으로 표현하는 것 자체가 새로운 클리셰
- 근거 없는 블루/그레이 디폴트 팔레트로 회귀
- 버튼/링크 텍스트에 "→" 습관적으로 붙이기
- 주제 섹션마다 팔레트/모티프를 다르게 적용 (1번, 4번 위반)
